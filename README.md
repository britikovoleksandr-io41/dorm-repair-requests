# Заявки на ремонт у гуртожитку

[Матеріали здачі та перевірок ЛР1–ЛР5](submission/README.md).

Мешканець повідомляє про несправність і бачить, що відбувається з його заявкою. Майстер переглядає чергу, бере заявку в роботу й закриває її після ремонту. Наприклад, мешканець повідомляє про кран, що протікає в спільній кухні, а з історії заявки видно, хто взяв її в роботу і коли ремонт завершили.

Проєкт починаємо з HTTP API на Node.js. Перший прототип використовує тестові дані в пам'яті. У наступній версії той самий API працює з PostgreSQL.

## Як працює заявка

Мешканець вказує місце, категорію й короткий опис несправності. Нова заявка має статус `open`. Коли майстер бере її в роботу, статус змінюється на `in_progress`, а сервіс записує виконавця. Закрити заявку може призначений майстер. Для переходу в `resolved` він залишає короткий опис виконаного ремонту.

| Дія                                          | Запит                        |
| -------------------------------------------- | ---------------------------- |
| Подати заявку                                | `POST /requests`             |
| Переглянути чергу за статусом або категорією | `GET /requests`              |
| Переглянути заявку та історію                | `GET /requests/:id`          |
| Взяти заявку в роботу                        | `POST /requests/:id/claim`   |
| Закрити заявку                               | `POST /requests/:id/resolve` |

Мешканець бачить власні заявки, майстер бачить чергу. Якщо двоє майстрів одночасно беруть одну заявку, лише один отримує її в роботу. Іншому API повертає `409 Conflict`. Історія зберігає попередній і новий статус, автора зміни та час. Якщо запис до історії не вдався, заявка лишається в попередньому стані.

Для зберігання достатньо `users`, `repair_requests` і `request_events`. Повтор `POST /requests` із тим самим ключем ідемпотентності й тими самими даними повертає вже створену заявку.

## Порядок роботи

1. **ЛР1. Основа застосунку.** У `spec.md` описати ролі, дозволені переходи, модель даних і межі між заявками та їхньою історією. У `standards/` зафіксувати формат специфікацій, ADR і перевірки перед здачею. Додати `GET /health`, форматтер, лінтер, збірку, smoke-тест і Git hooks. Перевірити блокування коміту з порушенням.
2. **ЛР2. Від черги в пам'яті до PostgreSQL.** Спочатку провести заявку від створення до закриття через усі маршрути прототипу й зберегти цей стан окремим комітом. Підключити PostgreSQL. У репозиторії умовно оновлювати заявку тільки з дозволеного попереднього стану й записувати подію історії в тій самій транзакції. Сервіс перевіряє ролі й право на дію, роут працює з HTTP. Додати глобальний обробник помилок і один business-process ID у логах запиту, сервісу, SQL-операцій та їхніх результатів. В ADR пояснити вибір БД і керування залежностями.
3. **ЛР3. Перевірка переходів.** Unit-тестами покрити дозволені й заборонені переходи статусу та умови доступу. Інтеграційно перевірити, що одночасне призначення має одного переможця, а збій запису події відкочує зміну статусу. E2E проводить заявку від створення мешканцем до закриття майстром і перевіряє історію. Запуск усього набору через `make test`, мутаційний прогін через `make mutation`. Для мутантів, які вижили, пояснити причину або посилити відповідний тест.
4. **ЛР4. Розгортання.** Налаштувати в GitHub Actions перевірки формату, лінту, збірки, тестів і Conventional Commits. Показати, що провал обов'язкової перевірки блокує merge. Після merge в основну гілку нова версія автоматично розгортається на публічному staging. Контейнер запускає міграції, CI використовує тестову БД. Через `/version` можна звірити SHA і вже на стенді перевірити чергу й перехід статусу на тестовій заявці.
5. **ЛР5. Виміри на заповненій черзі.** Підготувати набір заявок та історії. Повторити прогони `make load` і `make profile` для фільтрації черги та зміни статусу, зібрати p50/p95/p99, CPU, пам'ять і час очікування. Через `EXPLAIN ANALYZE` розібрати запит, що витрачає найбільше часу. Виміри визначають, яку частину винести в TypeScript-бібліотеку із залежностями через DI. Повторний прогін на тих самих даних дає порівняння з базовою лінією.

Кожна лабораторна має свій GitHub PR і окремий DEFENSE. Студент погоджує правила для `spec.md` і сам описує в DEFENSE, що перевірив та які результати отримав.

## Локальний запуск

Потрібні Node.js 22.15+ або 24 і npm.

```sh
npm ci
npm run hooks:install
npm run check
npm start
```

`GET /health` перевіряє, що HTTP-процес відповідає. Код, технічна документація й перевірки підготовлені за участю OpenAI Codex на основі опису проєкту та завдань курсу. Робочі інженерні рішення потребують погодження студента.

Для PostgreSQL вкажіть `DATABASE_URL`, зберіть код, застосуйте схему й налаштуйте `ACTOR_TOKENS`. Перед запуском додайте до `users` ID і ролі всіх налаштованих акторів. Значення токенів зберігайте в зовнішній конфігурації. Повний API на даних у пам'яті доступний у локальній гілці `feature/lab-02-static-api`.

```sh
npm run build
npm run migrate
npm start
npm run verify:db
```

`verify:db` піднімає ізольований PostgreSQL у Docker, якщо `DATABASE_URL` не задано. За наявності URL вказуйте окрему тестову БД. Контракт описано у [spec.md](spec.md).

## Тести

`make test` збирає проєкт, перевіряє гілки правил переходу, запускає smoke, інтеграційні та E2E тести. Потрібен Docker або чиста БД через `DATABASE_URL`. `make mutation` перевіряє тести правил переходу через Stryker і формує JSON та HTML у `reports/mutation/`. Перший і повторний прогони розібрано в [аудиті тестів](evidence/lab03-audit.md).
