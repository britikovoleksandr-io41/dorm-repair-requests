Для кожної ревізії на чистому коді виконано `make -s load` і `make -s profile`; stdout кожної команди збережено як відповідний JSON. Серія створювала нову PostgreSQL 17.11 у Docker і 120 360 заявок з 156 360 подіями. Для кожного режиму виконано три повтори, по 32 прогрівальні читання, 240 запитів черги майстра, 240 запитів черги мешканця, 120 claim і 120 resolve. Конкурентність — вісім клієнтів; фільтр — `open` і `plumbing`, 20 рядків, offset 0 або 40. Позавимірювальне застосування індексу зафіксовано в JSON після оптимізації.

## HTTP і SQL

У таблиці медіани трьох повторів кожного HTTP-перцентиля з `make -s load`; у дужках min–max трьох p95. Одиниці — мілісекунди.

| Сценарій | p50 / p95 / p99 до | p50 / p95 / p99 після | SQL p95 до → після |
| --- | --- | --- | --- |
| Черга майстра | 7,76 / 9,25 / 10,01 (9,13–9,27) | 1,50 / 2,96 / 3,37 (2,69–3,17) | 8,66 → 1,84 |
| Черга мешканця | 1,95 / 3,05 / 3,52 (2,54–3,23) | 1,76 / 2,44 / 3,04 (2,39–2,63) | 2,54 → 1,73 |
| Призначення | 3,37 / 5,23 / 6,90 (4,53–6,81) | 3,77 / 8,24 / 8,98 (5,58–9,74) | 4,44 → 6,41 |
| Закриття | 3,34 / 4,88 / 5,84 (4,84–5,61) | 3,68 / 5,11 / 6,30 (4,74–6,05) | 4,43 → 4,30 |

Час SQL — сума інтервалів від виклику `pg` до відповіді в Node для запиту HTTP. Він включає клієнтське очікування, мережевий шлях, виконання PostgreSQL і, для пулового SELECT, можливе очікування з'єднання. Для claim і resolve у сумі п'ять операцій із BEGIN/COMMIT; окреме отримання транзакційного з'єднання не входить до неї.

## EXPLAIN ANALYZE

- Черга майстра при offset 40. Seq Scan відкинув 114 713 і передав 5 647 рядків у top-N sort. План виконався за 5,858 мс і мав 2 621 buffer hit. Після індексу Index Scan видав 60 рядків у порядку ключів, Limit повернув 20. Час — 0,037 мс і 32 buffer hits. Кількість SQL-викликів для черги залишилася один.
- Черга мешканця. До індексу bitmap scan за мешканцем прочитав 2 235 кандидатів і відкинув 2 147. Після індексу BitmapAnd перетнув індекси, тож Bitmap Heap Scan отримав 88 збігів. Час — 0,817 → 0,569 мс, buffer hits — 2 009 → 152. Сортування залишилося.
- Індекс зайняв 7 315 456 байтів (6,98 MiB). Побудова на тестових даних тривала 85 і 92 мс у двох окремих серіях. Час і витрати staging залежать від розміру, I/O та конкурентних транзакцій.

## CPU, пам'ять і межі висновків

У `make -s load` сумарний CPU процесу Node за повтор становив 364–412 мс до і 350–405 мс після; peak RSS — 84,1–88,6 MiB до і 86,9–90,4 MiB після. У профільних повторах стан `(idle)` займав 48,8–53,3% від V8 sampling до і 17,5–24,3% після. З активних кадрів на базовій лінії помітні запуск Node і записи у потоки. Профіль охоплює весь процес і не вимірює CPU PostgreSQL. Відмінність HTTP від клієнтського часу SQL не дає чистий CPU-час окремого запиту.

### Аудит

1. Найповільніша базова операція — фільтрована черга майстра. У базових повторах її SQL p95 був близьким до HTTP p95, а план підтвердив витрати на сканування й сортування. Повторний план показав причину прискорення — індекс, який задає той самий порядок.
2. Після змін призначення мало гірший p95 за всіма відносними медіанами серій. Діапазони повторів частково перетинаються. Індекс оновлюється при переході статусу, а цей експеримент порівнює індекс і рефакторинг разом. Причина всієї зміни часу запису окремо не ізольована.
3. Винесений пакет отримує reader через DI, не залежить від драйвера та випускає декларації TypeScript. Реальний виграш часу не приписується винесенню бібліотеки. E2E перевіряє кордони черги для двох мешканців, а тест контейнера — завантаження пакета в runtime.

Середовище — локальний arm64 macOS, Node.js і Docker із версіями в JSON. Дані синтетичні, кеш БД прогрітий, HTTP локальний; staging потребує власного прогону після звірки SHA.
