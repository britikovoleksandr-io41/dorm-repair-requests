# Заявки на ремонт у гуртожитку

Робоча специфікація на основі наданого README. Правила нижче, яких немає в описі, підлягають погодженню студентом.

## Модулі

HTTP приймає запит, визначає ініціатора, перевіряє формат вводу й передає команду прикладному сервісу. Сервіс застосовує правила доступу та переходів. Репозиторій читає чергу й деталі, а також координує атомарний запис стану й події. Сервер збирає залежності на старті.

## Дані й сценарії

- `users` має ідентифікатор і роль мешканця або майстра. Один мешканець може створити багато `repair_requests`.
- Заявка має місце, категорію, опис, статус, автора й необов'язкового призначеного майстра. Ідентифікатор операції створення унікальний для мешканця.
- Заявка має багато `request_events`. Подія містить попередній і наступний статус, автора, час та примітку про ремонт для закриття.
- Мешканець створює `open` і читає власні заявки. Той самий ключ і ті самі дані повертають створену заявку.
- Майстер читає чергу й переводить `open → in_progress`. Конкурентні майстри отримують один успіх і один конфлікт.
- Призначений майстер переводить `in_progress → resolved` з описом ремонту. Відмова запису події відкочує зміну заявки. Закрита заявка має фінальний статус.

## Аудит ЛР1

`src/main.js` реалізує запуск і перевірку доступності, а наступна ревізія додає межу HTTP, сервісу й репозиторію. `test/smoke.test.js` перевіряє зібраний процес. Git hooks перевіряють файл зі staged-зрізу або дерево гілки, що передається до remote.

На цьому етапі відкладено HTTP-фреймворк (достатньо `node:http`), бібліотеку тестування (достатньо `node:test`) та ORM (схема й транзакції належать ЛР2). TypeScript виконує збірку, ESLint перевіряє JavaScript, Prettier забезпечує форматування.

## HTTP API

Запити до `/requests` містять Bearer-токен. Під час запуску сервер отримує JSON-масив `ACTOR_TOKENS` з полями `token`, `id` і `role`. Роль визначається конфігурацією сервера. Клієнт не може передати її окремо.

- `POST /requests` вимагає JSON з полями `location`, `category`, `description` та заголовок `Idempotency-Key`. Перше створення повертає 201, повтор із тим самим тілом після обрізання крайніх пробілів — 200, збіг ключа з іншим тілом — 409. Ключ має область одного мешканця.
- `GET /requests` фільтрує за `status` і `category`. Підтримуються категорії `plumbing`, `electrical`, `furniture` та `other`. Порядок — нові спочатку, при однаковому часі за ID у спадному порядку. `limit` від 1 до 100, типово 20. `offset` від 0 до 100000, типово 0.
- `GET /requests/:id` повертає заявку з подіями у порядку запису. Чужа заявка для мешканця має той самий код 404, що й відсутня.
- `POST /requests/:id/claim` бере заявку в роботу. `POST /requests/:id/resolve` приймає JSON з полем `note`. Неприпустимий перехід повертає 409, відсутність необхідної ролі або призначення — 403.
- Помилки формату повертають 400. Завелике тіло призводить до 413, тип тіла відмінний від JSON — до 415, а відсутній або недійсний токен — до 401. Відповідь містить `X-Business-Process-Id`, той самий ID використано в логах.

## PostgreSQL і відмови

`users` (PK `id`) посилається на ролі. `repair_requests` має PK UUID, два FK на користувача й UNIQUE `(resident_id, idempotency_key)`. `request_events` має PK identity, FK на заявку й автора та індекс `(request_id, id)`.

Створення робить `INSERT ON CONFLICT DO NOTHING`. Після конфлікту окремий SELECT читає оригінал і звіряє дані. Запис першої події входить у транзакцію створення. При claim/resolve PostgreSQL блокує рядок `FOR UPDATE`. Сервіс приймає рішення на зафіксованому стані. Репозиторій виконує умовний UPDATE і INSERT події. Помилка будь-якого запису викликає ROLLBACK. Клієнт повторює створення з тим самим ключем після невизначеного результату commit. Тимчасові збої PostgreSQL повертають 503, решта непередбачених помилок — 500. Сервер перевіряє з'єднання й відповідність ролей до прослуховування порту.

Черга читається одним SELECT з фільтром форми доступу, статусу й категорії. Деталі читаються одним SELECT з агрегуванням подій однієї заявки. Стан та історія належать до однієї видимої версії. Завантаження історії для кожного рядка черги спричинило б N+1. Через окремі ресурсні запити черга взагалі не читає подій. Перевірка ЛР2 контролює кількість SQL-запитів у логах.

### Аудит ЛР2

1. Токени видаються з конфігурації процесу. Для відкликання потрібна ротація конфігурації та перезапуск.
2. OFFSET підтримує прямий перехід до сторінки, але між запитами паралельні записи можуть зрушити сторінки. Сортування має стабільний другий ключ.
3. У прототипі немає реальних відмов запису. PostgreSQL-перевірка навмисно відхиляє INSERT події через trigger, перевіряє відкат і знімає trigger. Окремо обмежений timeout запиту перевіряється реальним табличним блокуванням.

## Перевірки ЛР3

Unit перевіряє таблицю переходів, ролі, належність призначення та примітку. Integration піднімає PostgreSQL і HTTP-процес, примусово створює конкуренцію за один рядок, а також перевіряє видимість стану після помилки події. E2E працює через HTTP зі справжніми токенами тестових акторів, проводить заявку через увесь цикл і читає її через другий процес, під'єднаний до тієї самої БД.

## CI та staging

Workflow `Verify and deploy` на PR і push у main перевіряє формат, лінт, збірку, smoke, unit, integration, E2E, Conventional Commits і збірку контейнера. Merge має вимагати зелений check `Verify`. Публікація образу й запуск deploy відбуваються лише після зеленого push у main. OCI digest задає образ, `GET /version` повертає його SHA, `GET /ready` перевіряє підключення до БД, `GET /health` показує доступність HTTP-процесу. `AUTO_MIGRATE=1` контейнера застосовує структурні міграції перед запуском HTTP. Клієнтські токени і staging DSN належать середовищу deployment.

Локальний негативний тест `make ci-negative` має завершитися помилкою форматування з кодом 1 від npm і 2 від make. GitHub workflow dispatch з `negative=true` запускає той самий крок на раннері. Захист гілки й перевірка на staging потребують окремого налаштування GitHub і Render.

## Навантаження ЛР5

У кожній серії окрема база Docker отримує детерміновані заявки й історію. Є три повтори із процесом Node.js для кожного. У кожному повторі працюють вісім паралельних клієнтів. Вони виконують 32 запити прогріву, по 240 запитів черги майстра та мешканця і 120 пар claim і resolve для різних заявок. Обидві черги фільтруються за `open` та `plumbing` на початковій сторінці й зі зміщенням 40. Сценарії виконуються послідовними серіями. SHA перевіряється через `/version` перед навантаженням.

`make load` збирає HTTP-перцентилі, сумарний виміряний час клієнта PostgreSQL за операціями запиту, CPU та peak RSS процесу Node.js. `make profile` застосовує той самий сценарій з V8 CPU sampling. Сирі значення, профілі та їхні SHA-256 зберігаються за SHA ревізії під `.lab-local/bench/`. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` використовує точний SQL застосунку для обох форм черги.

PostgreSQL-адаптер черги підтримує B-tree за статусом, категорією й порядком сторінки. Індекс застосовується окремо від структурних міграцій. Контракт `QueueReader` задає область видимості, фільтри, стабільний порядок, параметри сторінки й тип рядка.
