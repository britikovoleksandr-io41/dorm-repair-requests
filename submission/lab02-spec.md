# ЛР2 · Статичний API і PostgreSQL

**Мета** — провести заявку через усі п’ять маршрутів на статичних даних, а потім перенести зберігання до PostgreSQL із тим самим прикладним контрактом.

**Статус** — чернетка для погодження студентом. Категорії, HTTP-валидація, токени в конфігурації процесу, ліміти та OFFSET є робочими правилами. [Контракт API і даних](../spec.md#http-api) · [База даних](../adr/0001-postgresql.md) · [Контекст запиту](../adr/0002-request-context.md).

## Критерії приймання

1. У `c554532` після `npm run build` команда `node --test test/prototype.test.js` проходить без БД. Прогін охоплює створення, список, деталі, призначення й закриття.
2. У `c9f77a8` [перевірка PostgreSQL](../evidence/lab02-postgres.txt) підтверджує пару 201/200 з однаковим ID при одночасному створенні з одним ключем. Зміна тіла з тим самим ключем дає 409. Невалідний опис — 400, чуже читання мешканцем — 404, недозволена зміна — 403.
3. Два майстри отримують 200 і 409. Відмова INSERT події повертає 500 і лишає статус та історію в попередньому стані. Помилка доступності БД дає 503, після зняття блокування читання знову дає 200.
4. HTTP, сервіс і операції БД одного запиту мають однакові `businessProcessId` та ініціатора. Перевірка зіставляє заголовок і логи, включно з результатом запису події. Черга виконує один SELECT, історію читає окремий ресурс.
5. Документація позначає межі поточних рішень. Ротація токенів вимагає нового процесу. Сортування стабільне в одному запиті, а зміни між сторінками OFFSET можуть зрушувати результат.
