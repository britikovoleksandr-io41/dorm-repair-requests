# 0004. Типізована черга та індекс фільтра

Запропоновано до погодження.

## Контекст

Базова лінія `c44bf8e` на 120 360 заявках показала для черги майстра p95 HTTP 9,13–9,27 мс і p95 SQL 8,62–8,68 мс. `EXPLAIN ANALYZE` при offset 40 застосував Seq Scan і top-N sort, переглянув 120 360 рядків, знайшов 5 647 збігів та прочитав 2 621 буфер із кешу PostgreSQL. Черга мешканця вже використовувала індекс за ідентифікатором власника.

## Варіанти

Винести всі репозиторії або відокремити лише чергу. Для запиту розглянути зміну пагінації, кеш результатів і B-tree за двома фільтрами та ключами сортування. Відсутність спільних сторінок у мешканців обмежує користь кешування. Keyset змінив би контракт пагінації. Індекс зберігає поточний API.

## Рішення та наслідки

Workspace-пакет `@dorm/repair-queue` володіє областю видимості списку й контрактом `QueueReader`. Він компілює JS і `.d.ts` і не залежить від PostgreSQL, HTTP, конфігурації чи AsyncLocalStorage. Прикладний сервіс передає актора, а PostgreSQL-адаптер виконує рівно один запит і перетворює час на ISO. В іншому адаптері потрібні ті самі правила фільтрації, порядку та пагінації.

Індекс `(status, category, created_at DESC, id DESC)` відповідає виміряному запиту майстра. `npm run db:indexes` застосовує його конкурентно поза контейнерним стартом. Повторний запуск перевіряє стан індексу і відновлює невалідний після перерваної побудови. Індекс займає місце та оновлюється при зміні статусу. Повторні виміри охоплюють ці переходи.
